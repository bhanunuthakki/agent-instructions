# Conditional storage controls

These controls apply only to the corresponding operation or demonstrated failure. They are not an enrollment requirement for ordinary personal-app scratch files. Existing approved project recovery and retention policies remain authoritative.

## Large or repeated test allocations

Use an exact owned run root and the existing producer record when repeated bulk runs need accounting. Record source identity, expected peak, dependencies, and closure condition. Check older worktrees for stale allocation/cleanup controls before reusing them; port compatible controls without overwriting user work. Share only immutable inputs with matching content/schema identity. Writable rehearsals stay isolated.

If concurrent allocations can exhaust a volume, coordinate their projected peaks through the existing resource owner. Limits defer optional work; they do not delete unique data, stop live services, or weaken required verification. Choose budgets from observed workloads and available capacity rather than copying another host's thresholds. Distinguish active allocations from retained failure/recovery obligations. An absent process does not release an unresolved obligation. If retained reservations block ordinary verification despite ample capacity, review that policy with its owner instead of silently bypassing it or adding another reservation layer. Release reservations through their owner; release is not permission to delete payload.

Account for active peak reservations separately from bytes retained after a run. End an active lease through the producer's closure contract; retaining failure evidence need not reserve the run's full future peak indefinitely. Reclaim a departed holder's lease only through the owning mechanism with sufficient native identity evidence; denied inspection or possible PID reuse is uncertainty. Payload holds and real capacity/headroom checks remain independent of lease release.

## Concurrent maintenance and reconciliation

Keep one writer per affected resource. Reuse existing locks for backup, cleanup, retention, restore, and snapshot work. Before a long maintenance operation, check actual enabled owners and upcoming runs on the canonical host. Hold conflicting work when the invocation plus teardown would consume a protected maintenance window or its schedule cannot be established. A lock alone does not preserve that window.

Producer closure is primary. Use existing scheduled reconciliation only to recover missed closure and surface meaningful growth or retained obligations. Bound its own telemetry; suppress unchanged alerts. An overdue review triggers investigation, never deletion of unknown state. Preserve the original failure evidence and append its resolution.

## Backup retries and remote preservation

Distinguish local integrity verification, pending upload, confirmed remote preservation, and retention. A sync mount is not upload acknowledgment. Use a bounded pending queue and reuse unchanged artifacts. Preserve the last good verified recovery copy and protect changed authoritative state, or report backup failure. Do not silently drop changed state when a queue is full. Clean disposable task-owned staging on failure/interruption without touching backup pools owned elsewhere; a sole needed recovery or pending backup artifact is not disposable staging.

Evaluate retention per canonical source and recovery purpose, not per agent, checkout, or invocation. Reuse an adequate verified artifact when the source identity and freshness still match; new filenames do not establish new content. Keep additional local, historical, or remote copies only for the recovery coverage they provide. Exclude existing backup pools and reproducible transient trees from a new archive unless the recovery contract needs them, without excluding unique data by directory name. Keep application-specific counts, recovery windows, and required failure domains with the application; do not impose a universal snapshot count.

Use the database's supported snapshot/backup mechanism for live databases. Periodically restore into an isolated target. Never infer recoverability solely from archive existence or a successful process exit.

## Unique-state migration, conversion, or compaction

Decide what needs retention before converting it. Code rollback does not replace unique financial history, user decisions, or data-migration recovery. Preserve current references and their dependencies plus the recovery coverage required by the owning project; every historical copy need not survive.

Estimate net allocated-space benefit after replacement, recovery, and staging costs. Skip nonbeneficial conversion; an unknown estimate is not permission to create another bulk copy. Stop repeated admission after negative results and investigate. A skipped conversion does not count as completed preservation coverage.

Derived exports may separate stable content from capture metadata only when exact bytes, hashes, observation times, evidence identity, and provenance can be reconstructed and validated. Validate content before switching its current pointer. Do not invent missing capture indexes or discard source clocks to increase reuse. Keep partial-failure recovery and accounting with the publishing owner.

Deduplicate recovery snapshots by exact producer/snapshot identity. Preserve a qualified survivor and verify readers resolve it before retiring a duplicate. Compact only sealed inactive state under the existing owner lock and exclusive native handles. Verify full byte identity, metadata, decompression headroom, and a rollback path. Keep a durable intent and completion record for this operation. Do not alter live databases or directory inheritance. An unresolved recovery binding remains a hold.

An old code checkout or another database file is not automatically a substitute for a migration or row-level recovery anchor. Establish the exact required recovery window and dependencies before reducing snapshot history. Identical content may share storage only when distinct required observation metadata, provenance, and recoverability remain intact. A reference to an unverified or inaccessible survivor does not release the original.

## Verification scope

Exercise only the mechanisms changed: relevant cases include changed targets/survivors, permissions, links, active owners, reused branches, unchanged backup retries, changed durable state, and concurrent reservations. Verify installed source/configuration and native scheduler identity when deploying maintenance. The next genuine scheduled execution supplies recurrence evidence; a manual run cannot substitute for it.
